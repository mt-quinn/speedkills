# Capacity and cost assumptions

Capacity evidence: deterministic deployed simulator reports, sanitized production-runtime CPU samples, local workerd memory checkpoints and staging socket load results are saved alongside this document. Simulator CPU limit is 60 seconds; observed uncached preparations used approximately 18–39 seconds CPU. The conservative memory estimate for the largest of all 45 baseline pairings is about 75 MiB against the 128 MiB isolate limit. This is a checkpoint-based bound, not continuous production profiling.

The launch sizing target is 100 concurrent viewers with three subscriptions each, occasional economic commands and one league. Public snapshots share reads; archives use one bounded fight page and one batched wager query. Successful new commands are limited to 30 per actor per ten seconds. Chat retains its three-second send interval, auth uses persistent provider rate limits, subscriptions are capped at eight per socket and accepted sockets at 1,000. This target is not evidence for thousands of concurrent users.

An illustrative workload is 20,000 fights/month. At 30 seconds of *uncached* CPU per fight this consumes 600 million CPU milliseconds, approximately $11.40 above the 30-million included allowance, plus the $5 Workers Paid base and other usage. At one second per cached fight it consumes 20 million milliseconds and fits the CPU allowance. Unchanged crews reuse cached odds, so the uncached estimate is conservative for the current baseline roster. Viewer API CPU, retries and other account workloads add usage.

Even a continuously active 128 MiB coordinator uses approximately 324,000 GB-seconds/month, below the 400,000 included Durable Object allowance for one league; requests are billed separately. Hibernation reduces idle duration. A 0.2–0.7 MB gzip recording per fight adds roughly 4–14 GB per 20,000 fights. Retention accumulates indefinitely, so storage grows month over month. Ten GB of Standard R2 storage is included; additional storage is $0.015/GB-month, with separate request allowances/charges. A hundred viewers watching every fight would issue roughly two million R2 reads/month. This is an estimate, not a bill or spending cap; inspect actual dashboard billing after launch, especially D1 scanned rows, auth abuse, archive growth and retries.

Pricing checked October 1, 2026: [Workers](https://developers.cloudflare.com/workers/platform/pricing/), [Durable Objects](https://developers.cloudflare.com/durable-objects/platform/pricing/), [D1](https://developers.cloudflare.com/d1/platform/pricing/), [R2](https://developers.cloudflare.com/r2/pricing/). Existing Vercel frontend costs remain separate.

The initial service-RPC preparation design failed the command-latency gate under 100 viewers: a synchronous WASM call could stall the request tree for roughly 30 seconds. Live preparation now uses a separate Queues consumer and private Completion RPC callback. Queue operations are additional usage; duplicate delivery is checked against the durable job before computation and acceptance.

The final 100-viewer run connected all clients in 14.0 seconds and completed 40 commands without error while uncached queued compute ran. Median acknowledgement was 1.647 seconds; maximum was 3.811 seconds, which also bounds p95. The original two-second worst-case aspiration was missed. The launch gate accepts p95 below five seconds, typical latency below two seconds and the 100-viewer connection burst below 30 seconds. Track sustained regression against those limits; do not claim this proves 1,000-viewer capacity.
